## 构建命令与配置

执行 `npm run build` 时，npm 从 `package.json` 的 `scripts.build` 找到 `nuxt build`，Nuxt 再加载 `nuxt.config.ts` 中的项目配置。

| 脚本 | 当前命令 | 作用 |
| --- | --- | --- |
| build | `nuxt build` | 生成生产构建产物 |
| dev | `nuxt dev` | 启动日常开发服务器 |
| preview | `nuxt preview` | 本地预览已生成的构建产物 |
| postinstall | `nuxt prepare` | 安装依赖后准备 `.nuxt` 中的生成文件与类型配置 |

`postinstall` 属于安装生命周期，正常执行 `npm install` 或 `npm ci` 时会触发。它不表示每次 `npm run build` 前自动执行；与 build 对应的前置脚本名是 `prebuild`，当前项目未配置。因此，测量 `npm ci` 总耗时时，也会包含安装生命周期中的准备工作。[npm scripts 文档](https://docs.npmjs.com/cli/using-npm/scripts/)

在 `nuxt.config.ts` 中观察到：

- `modules` 加载了 `@pinia/nuxt`，用于接入 Pinia。
- `css` 全局引入 `main.css` 和 `post.css`。前者包含主题等公共样式，后者定义文章与 TOC 样式。
- **样式用途与加载范围不同：** post.css 虽然服务于文章详情，但目前被配置为全局引入，尚未限制为只在文章页使用。
- Tailwind 通过 `@tailwindcss/vite` 插件接入构建。
- `optimizeDeps.include` 配置了两个 Vue DevTools 相关依赖参与开发阶段的依赖预构建。看到配置不等于已经观察到执行或性能收益，开发预构建也不能作为生产包优化的证据。[Vite 依赖预构建文档](https://vite.dev/guide/dep-pre-bundling.html)

待验证假设：文章专用样式全局引入，可能增加其他页面的样式负担。后续通过生产产物和实际请求验证，当前不认定存在重复输出或已经获得优化收益。

## 页面组件链路

`app.vue` 是应用根组件，通过 `NuxtLayout` 与 `NuxtPage` 组织布局和当前路由页面。

```text
app.vue
├─ NuxtLayout
│  └─ default.vue（使用默认布局时）
│     ├─ NavBar
│     └─ slot
│        └─ NuxtPage → 当前页面
└─ NoticeContainer
```

- `default.vue` 提供默认布局，包括顶部栏和页面内容位置。
- `slot` 是布局预留的插槽；使用相同布局切换页面时，变化的是插槽内由 `NuxtPage` 展示的页面内容。
- `NavBar` 属于默认布局的共享结构。
- 登录页、注册页和管理员登录页都显式使用 `blank` 布局。
- `NoticeContainer` 位于 `NuxtLayout` 外，因此使用 blank 布局时仍在应用结构中。

### 检查与打包产物

```bash
test -f .output/server/index.mjs
tar -czf nuxt-output.tar.gz .output
```

第一行检查预期的服务端入口文件存在。这只是基础检查，不能证明应用能够正常运行；后续健康检查与浏览器测试提供进一步验证。

第二行把整个 `.output` 打包并使用 gzip 压缩，生成发布包。打包压缩耗时与 Nuxt 构建耗时需要分别记录。

### 理解 artifact

当前配置：

```yaml
uses: actions/upload-artifact@v4
with:
  name: nuxt-output
  path: nuxt-output.tar.gz
  retention-days: 3
```

这会把压缩包保存到 GitHub Actions 本次运行的产物中，名称为 `nuxt-output`，设置保留 3 天，供之后下载、检查或归档。上传 artifact 本身不会将应用部署到 VPS。[GitHub artifact 文档](https://docs.github.com/en/actions/tutorials/store-and-share-data)

```text
nuxt-output.tar.gz
├─ upload-artifact → GitHub 保存本次构建产物
└─ scp             → VPS 接收用于部署的压缩包
```

## 为什么部署整个 .output

当前项目采用需要 Nuxt 服务端运行的 SSR 部署方式，客户端资源和服务端程序都属于必要产物。

| 目录 | 主要内容 | 使用方 |
| --- | --- | --- |
| `.output/public` | JS、CSS、图标等公开静态资源 | 浏览器请求，服务器提供 |
| `.output/server` | 服务端入口、页面渲染代码及运行依赖 | VPS 上的 Node.js |

Node 部署入口：

```bash
node .output/server/index.mjs
```

Nuxt 服务端接收页面请求，执行 SSR 并返回 HTML。只上传 `.output/public` 会缺少当前部署方式所需的服务端程序。[Nuxt 部署文档](https://nuxt.com/docs/4.x/getting-started/deployment)

以直接访问文章页为例：

```text
浏览器请求 /posts/某篇文章
    ↓
VPS 上的 Nuxt 服务端获取文章数据
    ↓
Nuxt 渲染页面，返回 HTML
    ↓
浏览器加载 JS/CSS，完成 hydration
```

SSR 是在服务端生成页面 HTML，不等于所有页面都已在构建时预先生成。Nuxt 负责前端页面渲染，文章、登录、评论等业务 API 仍由独立 Worker 提供。

## 文章详情的数据请求链路

```text
app/pages/posts/[slug].vue
    ↓ 读取 route.params.slug，调用 PostApi.getDetail
app/services/posts.ts
    ↓ 确定 posts/<slug> 路径与 APIResponse 类型
app/composables/useAPI.ts
    ↓ 接入 Nuxt 数据获取管理，使用自定义 $api 发请求
app/plugins/api.ts 提供的 $api
    ↓ 执行 HTTP 请求，应用默认选项和拦截器
Worker API
```

这张图表示调用关系。插件在初始化时创建并提供 `$api`，不代表每次获取文章都重新执行整个插件。

### 两层 data 的含义

```ts
const { data } = await PostApi.getDetail(route.params.slug as string)
const payload = data.value?.data
```

- `data`：Nuxt 返回的响应式 Ref。
- `data.value`：完整的 `APIResponse<Posts | PostSlugRedirect>` 响应数据。
- `data.value?.data`：统一响应格式中的业务数据，即文章详情或重定向信息。

`useAPI` 的返回类型由 `createUseFetch` 推导，属于 Nuxt 的 AsyncData，包含 data、pending、error、status、refresh 等，并支持 await。给 useAPI 传入泛型是在描述预期类型，不会自动验证实际 JSON。

正常详情最终通过 `postDetail.contentHTML` 和模板的 `v-html` 展示。`PostSlugRedirect` 分支则处理文章旧 slug 的跳转，后续精简数据时必须保留。

### 请求地址与 baseURL 合并

假设 `apiBase` 为 `http://localhost:8787/api`，slug 为 `vue-reactivity`：

```text
baseURL：http://localhost:8787/api
服务层路径：posts/vue-reactivity
最终 URL：http://localhost:8787/api/posts/vue-reactivity
```

`$fetch.create` 设置的是请求实例默认配置，useAPI 则向这次调用传递配置。对 baseURL，底层先合并实例默认值和本次调用值，同名调用值覆盖默认值，再用最终的一个 baseURL 处理请求路径，因此不会拼接两次。

useAPI 中 `...callerOptions` 位于返回配置最后，调用者显式传入的 baseURL 可以覆盖它的默认值；实例默认值仍适用于直接调用 `$api` 的场景。Nuxt 还会使用 useFetch 配置中的 baseURL 参与自动生成数据 key。

### 为什么同时保留 useAPI 与 $api

| 调用方式 | 主要职责 | 项目中的使用场景 |
| --- | --- | --- |
| `useAPI` | 使用请求实例获取数据，维护响应式请求状态，并接入 SSR 数据传递与 hydration 复用 | 获取文章详情、列表等页面数据 |
| `$api` | 统一执行 HTTP 请求，提供默认地址、请求选项和拦截器 | 用户点击发布、删除、登录后执行操作 |

我的理解：获取文章详情需要维护页面数据和请求状态，并参与 SSR 与 hydration，因此使用 useAPI；发布文章由用户操作触发，需要明确控制提交时机和处理结果，因此使用 $api。

需要保留的边界：

- useAPI 不只在服务端执行，也能用于客户端导航或配置 `server: false` 的场景。
- useAPI 默认启动数据获取，但 hydration 可以复用数据，也可以配置 `immediate: false`；不能说每次 setup 都必然重新发请求。
- useAPI 同样支持 POST 等方法，不能单纯按 HTTP 方法划分两者。
- useAPI 是 composable，需要在合适的 Nuxt/Vue 上下文建立。取得 `$api` 实例后可以在事件回调等位置调用，但用于取得实例的 `useNuxtApp()` 本身仍有上下文要求。
- `$api` 本身不提供完整的 Nuxt payload 复用机制；使用它提交数据时，仍需处理提交状态、成功反馈和错误反馈。

```text
页面数据获取 → useAPI ─┐
                     ├→ $api → Worker API
用户操作提交 ─────────┘
```

Nuxt 的数据获取机制负责响应式状态与服务端数据向客户端的交付。[Nuxt 数据获取文档](https://nuxt.com/docs/4.x/getting-started/data-fetching)

### 正文、HTML 与 payload

直接请求文章页时，Nuxt 服务端获取正文，用它生成 HTML，并把所需数据写入 payload。浏览器可以先展示 HTML，再利用 payload 恢复应用数据并完成 hydration。

正文的直接展示来自 SSR HTML；payload 用于恢复客户端数据。在 key 对应且 payload 可用的正常场景下，可以避免 hydration 时重复获取相同数据。

站内导航通常由浏览器执行数据获取，是否产生新请求还取决于缓存等条件。因此，浏览器 Network 中没有文章 API 请求，不代表没有获取数据，请求也可能发生在 Nuxt 服务端。

### 评论请求与空状态

当前评论请求配置：

```ts
CommentApi.getList(postDetail.id, {
  server: false,
  lazy: true,
})
```

- `server: false`：评论不在 SSR 阶段获取，Nuxt 服务端无需等待评论接口返回才能完成正文页面渲染。
- `lazy: true`：采用不阻塞客户端导航的数据获取方式，本身不表示滚动到评论区才请求。

请求发起后 commentsResult 对象可以已经存在，而内部 data 仍未取得结果，因此 `commentsResult ?? '评论加载中'` 不能正确判断加载状态。

当前父页面通过 `commentsResult?.pending.value` 得到加载状态，并显示 Loading comments。与此同时，尚未取得的评论数据被转换成空数组；子组件只判断数组长度显示 No comments yet，存在加载提示与空状态同时出现的可能。这里只记录观察和改进方向，尚未修改或实测该行为。

除了 comments，评论组件还需要知道请求状态。正确的状态表达是：

| 请求状态 | 评论数据 | 应展示的内容 |
| --- | --- | --- |
| 等待或加载中 | 暂无数据 | 加载提示或占位 |
| 成功 | 空数组 | 暂无评论 |
| 成功 | 有评论 | 评论列表 |
| 失败 | 暂无数据 | 错误提示与重试入口 |

“暂无评论”的条件应为请求成功且数组为空。仅判断 `!pending` 不够，因为失败后也不再处于加载中。

## 实验复现与指标边界

### 为什么只记提交编号还不够

构建读取工作区里的实际文件，未提交修改也会参与构建；Git 提交编号只标识已提交的源码快照。

如果修改 `nuxt.config.ts` 后未提交就进行了测量，以后仅检出当时的提交，就无法恢复该配置修改，可能无法复现产物。因此 baseline 需要能恢复实际测量的源码，包括适用的未提交差异和新增文件。

### 删除未进入浏览器产物的依赖，哪些指标会变

| 指标 | 正确判断 |
| --- | --- |
| 安装时间、node_modules 体积 | 可能减少；如果仍被其他包间接依赖，可能不会完全移除 |
| 生产构建时间 | 取决于构建过程是否使用或处理该依赖，不能保证改善 |
| 开发服务器启动时间 | 取决于启动过程是否加载或预构建该依赖，不能保证改善 |
| 客户端 JS 体积 | 如果原本没有进入客户端产物，通常不变 |
| 整个发布包体积 | 仍可能变化，因为该依赖可能进入服务端产物 |

判断前先追踪：依赖位于哪条引入链，参与安装、开发、构建还是运行阶段？然后按对应指标测量。

### 我的回答：服务端产物减少 2 MB 是否等于首屏少下载 2 MB

不能。`.output/server` 是运行在服务器上的 Nuxt SSR 代码，本身不会作为客户端资源发给浏览器。

更准确的表述是：Nuxt 服务端生成 HTML 并返回浏览器。如果浏览器实际请求的 HTML、JS、CSS 都没有变化，就不能声称首屏下载量减少了 2 MB。

服务端产物变小可能影响发布包体积、上传成本或服务端运行表现，但这些需要单独测量；也不能由“下载量不变”直接推断所有加载耗时都不变。
